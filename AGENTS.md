# AGENTS.md

Guidelines for any agent working in this repository. Read this, then
[docs/03-roadmap.md](docs/03-roadmap.md) for what is open, then
[docs/02-implementation-plan.md](docs/02-implementation-plan.md) and
[docs/00-requirements.md](docs/00-requirements.md). If this file conflicts with requirements,
requirements win for *what*; this file wins for *how*.

`STATE.md` is a **project** brief, generated by `bench state` inside a project folder. This repository
is the application, not a project: there is no `STATE.md` here, and running `bench state` at the
repository root is a refusal, not a missing file. A project folder always has one, and it is the first
thing a session opened *there* should read.

## What this project is

A durable data-analysis workspace for Windows. An append-only event log holds the truth; a `bench`
CLI is the only way to mutate it; an Electron app is the viewport onto it ([ADR 0005](docs/adr/0005-desktop-shell.md)).
An agent operates it on the user's behalf, so a fresh session must be able to pick up the project
without re-litigating it.

## Non-negotiables

1. **Never edit `data/events.jsonl` directly.** All mutations go through `bench`.
2. **Never mutate `data/raw/`.** Imported files are evidence.
3. **Never delete a dataset version.** Replacing data creates a new version with a diff.
4. **Never put analysis in the entry path.** Typing a number must not wait on Python or a model.
5. **Never mix observed and derived values.** Fitted values never enter a dataset.
6. **Never draw a curve without n, DOF, an interval band, and a verdict.**
7. **Never change a point's shape silently.** Extending a shape is a recorded migration.
8. **Never make the log's vocabulary the window's vocabulary.** Record ids, event names, dataset and
   shape ids, versions and hashes are for the agent and for copied details. The window shows values,
   units, what changed and what to do; every term that is not obvious is explained on hover
   ([ADR 0015](docs/adr/0015-user-surface.md)).

## Running it

- **CLI**: `pnpm bench <command>` (or `node src/cli/index.ts <command>`).
- **Desktop window**: `pnpm app` — builds the core and CLI bundles with esbuild, then launches Electron.
  `pnpm app:capture` does the same and writes review frames to `docs/ui-review/`.
  `pnpm app:measure` builds a 10k-point project and reports keystroke→paint in the real window.
  `BENCH_APP_PROJECT=<dir> pnpm app` opens a specific project on launch (`BENCH_PROJECT` is the
  capture harness's input, which it forwards).
- **Standalone build**: `pnpm app:package` writes `artifacts/bench-win32-x64/bench.exe` — no installer
  ([docs/packaging.md](docs/packaging.md)). It runs `install-electron` first, so Electron's runtime is
  fetched on demand (Electron 44 dropped its postinstall) and then copied from `node_modules/electron/dist`.
  The artifact also carries `bench.cmd`, the same CLI run by its Electron binary in Node mode; it is
  the way an agent operates a project without this repository. `pnpm app:package:check` launches the
  artifact and its CLI with Python removed from `PATH`, and fails unless both work. It compares the
  run against the committed receipt (`docs/ui-review/app-packaged.json`) and writes that file only
  with `--record`, so a plain run leaves the tree clean.
- **Everything else**: `pnpm verify` (typecheck, bundle, tests), `pnpm fixture`, `pnpm review`.

## How work gets done

- **Small steps.** One user-visible capability per step. Aim for a diff under ~400 lines, reviewable
  in 10 minutes. If a step needs to be bigger, split it.
- **Plan, then build, then verify.** State the intended behavior before writing code. Test the
  behavior you claimed, not just the exit code.
- **UI work is gated on the user.** Produce a screenshot and a row that answers four things — what
  this is, the one check, what wrong looks like, the decision wanted — at 100/125/150% scaling, and
  wait for approval. Never self-approve a visual change. Log it in `docs/ui-review-log.md` under the
  protocol there. The user may close a batch of frames by stating a direction instead of approving
  each one; record their words, and treat that as a decision about the direction, not as a claim that
  every pixel was inspected.
- **Say what was assumed before a write, and what changed after it.** When a mutation rests on a guess
  — which column holds the time, a missing field, an estimated instant, a dropped column — state it in
  one sentence and ask if the answer would change the data. Afterwards, summarise the change in plain
  words. Routine, reversible actions the user already asked for need no second confirmation
  ([ADR 0015](docs/adr/0015-user-surface.md)).
- **Record irreversible choices** as a short ADR in `docs/adr/` before acting on them. The load-bearing
  ones: [0001](docs/adr/0001-stack-choices.md) stack, [0002](docs/adr/0002-agent-only-v1.md) agent-only
  v1, [0003](docs/adr/0003-in-process-core.md) the write path is in process.
- **Don't add dependencies silently.** Name the dependency, say why, and note the size cost.
- **Update a project's `STATE.md`** by running `bench state` in that folder after any mutation — never
  by hand. (Not this repository: it has no `STATE.md`.)
- **Record decisions** the user makes ("we're using Python", "tabs instead of a sidebar") via
  `bench decide` in the project, so the next session inherits them. Decisions about the *application*
  itself belong in `docs/adr/` and the roadmap.

## Version control

- **`pnpm verify` means green.** It runs the typecheck and the tests. Never commit on red.
- **Commit at every good point**: each completed step, each fixed bug, each decision recorded. A
  green check plus a clean tree is the bar for ending a pass.
- **Never leave uncommitted work behind.** If a step is half-done, either finish it or revert it;
  a broken tree costs the next session more than it saves.
- **State what changed and why** in the message, and name anything deliberately left out.
- **Never rewrite history** on a branch someone else may have built on. There is one branch until
  the user asks for more.
- Regenerable output is ignored (`artifacts/`, `index.sqlite`, `node_modules/`). If a file can be
  rebuilt in one command, it does not belong in history — except fixtures, which are committed so
  the tests have something real to read.

## Definition of done

A step is done when all of these hold:

- [ ] The claimed behavior works through the interface the user actually uses.
- [ ] Tests cover it; stats code is checked against a closed-form or reference result.
- [ ] Empty, loading, error, and single-point states all render sensibly, and each actionable state
      has a button (a CLI command may appear only inside a collapsed "for agents" detail).
- [ ] No id, event name, version list or internal identifier appears in a primary label, tooltip or
      status; anything non-obvious is explained on hover; no fact is shown twice.
- [ ] Every reversible action it adds is covered by undo, and redo works.
- [ ] Keyboard-only path works; focus is never lost or trapped.
- [ ] Renders correctly at 100/125/150% scaling.
- [ ] No layout shift or flicker when data updates.
- [ ] Perf budget respected: keystroke→paint < 100 ms, re-render < 50 ms at 10k points.
- [ ] No new dependency without a note.
- [ ] `bench check` passes.
- [ ] The row this closes in [docs/03-roadmap.md](docs/03-roadmap.md) is updated in the same commit, with
      the evidence that proves it — or, for a new gap found on the way, a new row.

## Visual standard

Clean, calm, dense-but-breathable. One accent color. Numbers set in a tabular/monospace face.
Charts use a restrained palette with a single emphasis hue. No gradients, no drop shadows on cards,
no icon without a label in primary flows. Design tokens live in one file; never hardcode a color or
spacing value in a component.

The app should look like an instrument, not a dashboard template.

**Explain in place, at the level of the consequence.** A status word that is not self-evident says what
it means for the reader: why this is uncertain, what would strengthen it, what they can do. A badge
that asks nothing ("current") is not shown. Duplicate facts are removed, not restyled: a fact appears
at the level where it applies — the tab name in the header, a panel's `n` in the panel, the dataset
size once when panels disagree. A single dataset named `main` is not information.

**The window is for a person; the log is for the agent.** Values, units, plain sentences and actions
on screen; ids and event names only in what a person explicitly copies. The user does not need to
understand the log, and must not be asked to enforce its integrity; that is the agent's job
([ADR 0015](docs/adr/0015-user-surface.md)).

## Where things live

**Two layouts. Do not confuse them.** This repository is the *application*. A user's *project* is a
folder somewhere else, created by `bench init` and opened by `bench --project <dir>`.

This repository (the app):

```
src/core/           log, binder, shapes, chart spec, state, Python runner — no UI imports
src/core/workspace.ts
                    the one in-process path to a project: every mutation and analysis goes
                    through it, and the CLI is a wrapper over it (ADR 0003). The app will bind
                    this directly; it must never learn about windows or drawing.
src/cli/            the bench command surface — argument parsing, a call, and printing.
                    Domain commands live in their own modules (shape.ts, import.ts, view.ts);
                    index.ts dispatches and owns process-level concerns such as exit codes.
app/                the desktop shell (ADR 0005): Electron main + preload + renderer, and
                    core.entry.ts, which is bundled to app/core.bundle.mjs by `pnpm app:build`
                    (the same command bundles src/cli to app/src/cli/index.mjs for the artifact).
                    workspace-session.ts keeps the open Workspace; view-session.ts owns a view from
                    construction through its cached, staged and saved states; core.entry.ts is the
                    IPC facade over them. main.js is the window, the IPC surface and the boot
                    switch; harness/ holds capture, measure and smoke, which drive that window.
app/renderer/       the viewport, split by concern. app.js is wiring and the open-view lifecycle
                    only; state.js owns shared state and the core call; copy.js owns every word
                    a person reads (ADR 0015) and no other module composes a sentence;
                    rail.js owns projects/tabs/folder; panels.js owns the panel mount and statuses;
                    entry.js owns typing, correction and undo; tabs.js owns the tab sheet;
                    projects.js owns the project sheet; import.js owns the import sheet;
                    navigation.js holds the few shell actions that cross a module.
                    Remaining window work lands here: resizable/collapsible rail in rail.js, the
                    point menu and readable tooltip in chart.js with its actions in entry.js, undo/redo
                    in entry.js, tab and project management in tabs.js/projects.js, entry extras in
                    entry.js, versions panel beside panels.js, and preferences in state.js + the main
                    process ($BENCH_HOME/ui.json).
src/core/registry.ts
                    which projects exist on this machine ($BENCH_HOME/projects.json, outside every
                    project). App state, disposable: losing it loses recency, not data.
src/core/views.ts   the tab file format (§4): schema validation, storage, and grid rendering
src/core/panels.ts  what a panel reads and draws: row selection, materialization, staleness
src/core/import-columns.ts
                    the import column policy: mapping, the time column, undeclared columns
src/core/shapes.ts  shape declarations and version transitions (extend, designate, latest)
src/core/axes.ts    which declared fields each axis reads, and whether x is a clock
src/core/hints.ts   the one "what next" command derived from a declared shape
src/core/observation.ts
                    the one decision about a point's observation time
recipes/            the Python analysis library, pinned by requirements.lock.txt
recipes/.venv/      the analysis environment, recreated by `pnpm setup:recipes` (ignored)
tests/              unit tests, plus CLI tests that run the real binary
fixtures/projects/  committed demo projects, rebuilt by `pnpm fixture`
docs/               requirements, plan, roadmap, ADRs, the user-surface register, UI review log
```

A user's project:

```
data/events.jsonl   truth (append-only, via bench only)
data/raw/           untouched imports
shapes/             point shape registry (declared in the log)
views/              one JSON file per tab (`<slug>.json`), rendered by `bench view render`
artifacts/          generated output, all regenerable
index.sqlite        derived index, disposable (not built yet)
AGENTS.md           this project's own rules, written by `bench init`
STATE.md            generated cold-start brief — never edit by hand
```

`docs/03-roadmap.md` is the one list of open work. When the plan's progress table and the roadmap
disagree, the roadmap is newer; fix the plan rather than keeping two answers.

Recipes are **app-level**, not per-project: they are the analysis library bench ships, versioned and
pinned. A project owns data, shapes, views and decisions. Per-project recipes are a later feature.

## Working on a project from this workspace

A session does not need a new workspace for every project. When the user names a project, or a
`bench` command targets one, read that project's `AGENTS.md` and `STATE.md` **before the first
mutation**. If the project is outside this workspace and its files are not readable, run
`bench --project <dir> state` and use its output as the brief; the project's own `AGENTS.md` names
the launcher. This repository's `AGENTS.md` governs the application, never the project's data,
shapes, views, or decisions. Do not infer a project's conventions from this file.

This is a written rule, not a runtime gate: `bench` cannot prove that an agent read the brief. The
failure it prevents is concrete — a wrong shape, a re-litigated decision, or a mutation against the
wrong project — and the generated `STATE.md` is the thing that makes the rule cheap to follow.
Opening the project folder as its own workspace is still the strongest option for a long session;
this rule covers the convenience case where the agent stays here and reaches the project by path.

## When in doubt

Prefer the change that makes the next session easier to start. Prefer a visible limitation over a
confident guess. Ask the user before an irreversible choice, not after.
